# Building SlopAMP

Developer notes. The user-facing introduction is in [README.md](README.md).

## How it works

```
Electron (Chromium UI)  ── src/renderer/  index.html · winmgr.js · skins.js · app.js · panel.html
                                          skins/*.css · frame.css · style.css
   │  IPC (preload.js, contextIsolation + sandbox)
Main process            ── src/main.js     state, playlists, downloads index, media keys
   ├─ WindowManager     ── src/windows.js  where the windows are: snapping, docking, presets, saved layout
   ├─ Downloader        ── src/downloader.js  yt-dlp queue (one at a time, self-updating copy)
   └─ MediaServer       ── src/media.js    127.0.0.1-only HTTP server:
         /app/*   UI files (an http origin so the YouTube embed gets a valid referrer)
         /f/KEY   local file with Range support (MP4/H.264, WebM, MP3, FLAC, WAV, OGG, AAC)
         /s/KEY   FFmpeg live remux/transcode → fragmented MP4 (MKV, AVI, ProRes, WMV, HEVC, AC3…)
                  encoder auto-picked: NVENC → AMF → QuickSync → Media Foundation → OpenH264
                  (Linux: NVENC → VAAPI (libva 2.21+) → Vulkan → OpenH264)
         /v/KEY   subtitles converted to WebVTT
```

- **Windows** (1.3): the player, equalizer, video/visualizer and playlist are four real windows. `index.html` holds all the content; `winmgr.js` wraps each panel in a window frame, opens the other windows with `window.open('panel.html', id)` and moves their frames into them, then starts `app.js`. Same-origin windows opened this way share the player's renderer process, so `app.js` drives every window directly (one `<video>`, one AudioContext, the YouTube player and Butterchurn all keep working across windows). Rules for code in `app.js`:
  - find elements with `$` / `$$` (they search every window), not `document.querySelector`;
  - listen with `WM.onDocs(type, fn)` / `WM.onWins(type, fn)` for document/window events that should work in any window;
  - `<body>` classes go through `WM.body` so every window gets them;
  - popup menus open with `WM.popup(el, { doc, x, y, flipY, above })`: they live in a hidden always-on-top `popup` window so they can stick out of small windows. Dialogs (`showModal()`) open in their own `dialog` window the same way;
  - show/hide/roll up windows with `syncWindows()` (it calls `WM.setPanels`).

  `src/windows.js` (main process) owns the geometry: it moves windows for title-bar drags and the resize grip/edges (it follows `screen.getCursorScreenPoint()` until the mouse is released), snaps edges within 10 px to screen edges and other windows (edge to edge, never overlapping), moves the windows docked to the player along with it, moves windows docked underneath a window that grows, shrinks, appears or disappears, applies the Layout presets and Reset layout, and resets the layout when a window ends up off screen. The layout is saved in the state file under `layout`:

  ```
  "layout": { "version": 1, "skin": "default", "preset": "classic", "snap": true, "onTop": false,
              "windows": { "main": {"x":..,"y":..,"w":..,"h":..}, "eq": {...}, "video": {...}, "playlist": {...} },
              "heights": { "main": 171, ... } }
  ```

  `skin` is the chosen skin's id (see below); the lightning bolt and Reset layout never change it. `panels.skins` is where the skin picker was dragged to (movable popups pass `remember` to `WM.popup`; `windows.js` keeps them on screen). `heights` are the on-screen heights (a rolled-up window is only its title bar). Which windows are open or rolled up is renderer state (`showVideo`, `showPlaylist`, `eq.panel`, `vis.panel`, `plShade`, `vidShade`). On the first 1.3 launch the layout is built from 1.2's `window` and `plHeight` keys.
- **Skins** (1.4): every colour, glow, border, background, font and size is a CSS variable. `src/renderer/skins/classic.css` is the default "SlopAMP Classic" skin and defines all of them; `style.css` (window contents) and `frame.css` (title bars, borders, resize grips, snap highlights, the popup/dialog windows) only use those variables, and the canvas drawings (clock, state icon, spectrum, EQ curve, BARS) read theirs with `WM.token('--name')`. The other skins (`skins/<id>.css`) are loaded after `style.css` and override what they change; they're generated by `build/skins/make_skins.py` (colour transforms of Classic plus hand-picked values and a few extra rules), so edit a skin there and re-run it. `src/renderer/skins.js` has the list of skins, switches them (it swaps one `<link id="skinCss">` in every window, then redraws the canvases) and builds the picker; the choice is saved as `layout.skin`. To add a skin: add it to `make_skins.py` and to `SKINS` in `skins.js` (with its preview colours). Window frames are built in one place (`FRAMES` / `buildFrame()` in `winmgr.js`). The only colour outside the skins is the main process's `backgroundColor`, which shows for a moment before the page paints.
- **State** (playlists, tabs, settings, download index, window layout) lives in `%APPDATA%\SlopAMP\slopamp-state.json`. The portable exe uses `SlopAMP Data\` next to the exe instead. Linux: `~/.config/SlopAMP/slopamp-state.json` (with `slopamp.log`); the AppImage uses a `SlopAMP Data` folder next to it only if one exists (its `AppRun` sets `SLOPAMP_DATA_DIR`).
- **Downloads** go to `Downloads\SlopAMP\Video`, `\Audio`, and playlists to `\Playlists` (Linux: `~/Downloads/SlopAMP/…`, the XDG Downloads folder). Every downloaded file is named `Title [VIDEOID].ext`, so SlopAMP can re-find copies from the folders alone.
- **Updates** (`src/updater.js`): at most once a day (10 s after launch) the main process asks `api.github.com/repos/SlopAMP/SlopAMP/releases?per_page=20` (3.2.0; before: `/releases/latest`) for the newest release for its platform. The installed build downloads the `SlopAMP-Setup-X.Y.Z.exe` asset into `%TEMP%\SlopAMP-update`, checks its SHA256 against the `SHA256 (SlopAMP-Setup-X.Y.Z.exe): <hash>` line in the release notes, checks it again just before running it, quits normally (window closed, state saved, "quitting" in the log), and only then, from `will-quit`, runs `SlopAMP-Setup-X.Y.Z.exe /S /UPDATE /PID=<pid> /D=<folder SlopAMP runs from>` (so a custom install folder is kept; `/D=` must stay last and unquoted). In `/UPDATE` mode the installer waits for that process to exit (it writes its steps to `slopamp.log` as `installer: …`), keeps the desktop-shortcut choice, and reopens SlopAMP. Before installing (and uninstalling), the installer looks for any SlopAMP window or SlopAMP.exe process, including hidden ones and the portable exe's copy in `%TEMP%`. It asks them to close (WM_CLOSE), and ends them with `taskkill` if they're still there after 10 s. Interactive runs ask the user first. A release without that line, or without the Setup asset under `https://github.com/SlopAMP/SlopAMP/releases/download/vX.Y.Z/`, is refused. The portable exe (`SLOPAMP_PORTABLE=1`) and dev runs only open the release page. **Linux (3.2.0):** the AppImage downloads `SlopAMP-X.Y.Z-x86_64.AppImage` the same way (SHA256 line `SHA256 (SlopAMP-X.Y.Z-x86_64.AppImage): <hash>`) and, from `will-quit`, copies it next to the running AppImage (`APPIMAGE`), checks it again, renames it into place (a file name with a version in it becomes the new file name and the old file is deleted; any other name is replaced in place), and starts it with `/bin/sh` once SlopAMP's process has exited (`updater.js` `swapAppImage`). It needs a writable folder; otherwise, and for the .deb, an unpacked folder or a dev run, SlopAMP only opens the release page. **Per platform (3.2.0):** SlopAMP reads the list of releases (`/releases?per_page=20`, not `/releases/latest`) and takes the newest full release that has this platform's files: a release with nothing for this platform (no `.exe` on Windows; no `.AppImage` / `.deb` on Linux) is skipped quietly. A release that has a file for this platform but not the one needed is still an error, as before. GitHub's "latest" mark only matters to copies older than 3.2.0, which read `/releases/latest`. Settings live under `update` in the state file: `mode` (`auto`/`notify`/`off`), `lastCheck`, `skipped`, `dismissed`, and `pending` (the version being installed, so the next launch can show "Updated to X").
- **Visualizer:** `src/renderer/vendor/` holds the Butterchurn bundle and presets. `build/butterchurn/build.sh` rebuilds them from the upstream sources. Preset equations are precompiled so the app's Content-Security-Policy can forbid `eval`.

## Developing

On Linux (3.2.0) with Node.js installed:

1. `bash build/fetch-linux-tools.sh` downloads the pinned Electron, FFmpeg (BtbN `linux64-lgpl-shared`), yt-dlp and AppImage tools into `vendor/linux-tools` (checking each SHA256) and links `vendor/ffmpeg/linux` (`bin/` + `lib/`) and `vendor/ytdlp/linux/yt-dlp` for a checkout.
2. Run `vendor/linux-tools/electron-linux/electron .` On a Wayland desktop SlopAMP restarts itself once with `--ozone-platform=x11` (it places its own windows, which Wayland doesn't allow); `SLOPAMP_WAYLAND=1` keeps Wayland.

On Windows with Node.js installed:

1. Put FFmpeg in `vendor\ffmpeg\win32\` (`ffmpeg.exe`, `ffprobe.exe` and DLLs from a [BtbN LGPL shared build](https://github.com/BtbN/FFmpeg-Builds/releases)).
2. Optionally put `yt-dlp.exe` in `vendor\ytdlp\win32\` for the Download button.
3. Run `npx electron@45.3.3 .`

## Building the installers

The release build runs on Linux (or WSL) and uses Wine for `rcedit` and to read the bundled FFmpeg's and yt-dlp's versions:

```
bash build/fetch-win-tools.sh                          # once: the pinned tools in vendor/win-tools
TOOLS=vendor/win-tools bash build/build-win.sh
```

`build/fetch-win-tools.sh` (3.2.1) downloads the pinned tools, checks each file's SHA256 and unpacks them into the layout below (`TOOLS`, default `vendor/win-tools`; the archives stay in its `downloads/`). FFmpeg and yt-dlp are the same releases as the Linux build's (`fetch-linux-tools.sh`). `TOOLS` contains:

- `electron-win/`: unzipped `electron-v45.3.3-win32-x64.zip` (from Electron's GitHub releases)
- `ffmpeg-win/<dir>/`: BtbN `ffmpeg-N-129046-g3a78197c4c-win64-lgpl-shared` (autobuild-2026-11-18-12-39, as on Linux); exactly one folder
- `ytdlp/yt-dlp.exe`: yt-dlp 2026.10.26
- `nsis/`: electron-builder-binaries `nsis-3.0.4.1` (with its Linux `makensis`)
- `rcedit-x64.exe` (v2.0.0) and `wine-11.2-amd64-wow64/` (Kron4ek's Wine build); `wineprefix/` is made on the first run

The versions in the licenses and FFmpeg's written offer come from the Windows files that ship: FFmpeg's from the BtbN folder's name, checked against what its `ffmpeg.exe` reports (which adds the build date), and yt-dlp's from `yt-dlp.exe --version`; the build stops if either can't be read (3.2.1; before, they came from a Linux FFmpeg and yt-dlp, which could be other builds).

`build-win.sh` also writes `dist/uninstall-files.nsh` with `build/make_uninstall_list.py`: one `Delete` per installed file and an `RMDir` (empty folders only) per folder. The uninstaller uses only that list and never deletes the install folder recursively, because it may be shared. `installer.nsi` refuses to compile without it.

Outputs go to `dist/`: the app folder, `SlopAMP-Setup-<version>.exe`, `SlopAMP-Portable-<version>.exe` and a zip.

## Building the Linux packages (3.2.0)

On Linux, without root:

```
bash build/fetch-linux-tools.sh       # once: the pinned tools in vendor/linux-tools
bash build/build-linux.sh             # TOOLS=vendor/linux-tools by default
```

It needs python3 (with Pillow for the icon sizes; without it only 256 and 512 px icons), `dpkg-deb` (1.19+, for `--root-owner-group`) and Node (to read `package.json`). `build/linux/` holds the launchers, the menu entry, the AppStream file, the AppArmor profile and the .deb's `postinst` / `postrm`. Outputs go to `dist/`:

- `SlopAMP-linux-x64/`: the app folder. Electron renamed to `slopamp`, English locales only (as on Windows), `resources/app`, `resources/ffmpeg/bin` (ffmpeg, ffprobe) + `resources/ffmpeg/lib` (their LGPL libraries, found through RPATH `$ORIGIN/../lib`), `resources/ytdlp/yt-dlp` (yt-dlp_linux), `licenses/` and `THIRD_PARTY_NOTICES.txt` (`make_licenses.py … linux`: Linux paths, the AppImage runtime added) and `README.txt` (`make_readme_linux.py`: README-users.txt in Linux words).
- `SlopAMP-<version>-amd64.deb`: `/opt/SlopAMP`, `/usr/bin/slopamp` (adds `--ozone-platform=x11`), `/usr/share/applications/com.slopamp.SlopAMP.desktop`, hicolor icons, AppStream metadata and `/usr/share/doc/slopamp/copyright`. `chrome-sandbox` is setuid root. `postinst` copies `resources/apparmor-profile` to `/etc/apparmor.d/slopamp` (an unconfined profile with `userns`, as Ubuntu ships for Chrome and VS Code) only where `apparmor_parser` accepts it (Ubuntu 23.10+, which needs it), and loads it; `postrm` removes it. `MAINTAINER=…` sets the control file's Maintainer (default `SlopAMP <slopamp@slopamp.com>`, the project's contact address).
- `SlopAMP-<version>-x86_64.AppImage`: the app folder at the AppDir's root without `chrome-sandbox` (an AppImage can't be setuid), the pinned type2 runtime (no libfuse2 needed) and `AppRun`. `AppRun` adds `--ozone-platform=x11`, sets `SLOPAMP_DATA_DIR` for a `SlopAMP Data` folder next to the AppImage, and checks whether this process may create a user namespace with its own root user (`unshare --user --map-root-user true`): Ubuntu 23.10+ refuses that to programs without an AppArmor profile, and then SlopAMP runs with `--no-sandbox` and `SLOPAMP_NO_SANDBOX=1` (logged; shown in "?").
- The release-note SHA256 lines for both files.

**Electron's Linux binary is patched** (`build/patch-electron-linux.py`, run by `fetch-linux-tools.sh` on `vendor/linux-tools/electron-linux/electron` and checked again by `build-linux.sh` on the staged `slopamp`): two fixes to Chromium 156's X11 drag and drop, which on a Wayland desktop is what a link dragged in from Chrome goes through (GNOME's XWayland bridge). (1) `ui::RefCountedMemoryToString16()` fails a CHECK, and the whole app dies, on a selection with an odd byte count, and Chrome on Wayland sends `text/x-moz-url` as UTF-8, so about half of Chrome's links crashed SlopAMP; patched to return no text instead (as upstream Chromium dabcf3ee8b11 does, in Chromium 159+). (2) `ui::XDragContext::OnXdndPositionMessage()` clears the data it has fetched and asks again for each XdndPosition that comes during the fetch, and GNOME sends one per pointer motion, so drops from Chrome often came with no data at all; patched so a position during the fetch only moves the drop point (two short sequences, the second in the int3 padding after `RequestNextTarget()`). The script works only on the exact Electron 45.3.3 linux-x64 binary (its SHA256), checks every byte it replaces and the result's SHA256 (`f8b970bf…`), and stops for anything else. **When Electron is updated:** check whether its Chromium has both fixes (drop the step) or find the two places again (`tests/linux-dnd-320.js` reproduces both: the crash and the empty drops).

**Drags from other apps on Linux X11** (`x11.js` `xdndAccept`, called from the page's `dragover` through `dnd:accepted`): Electron answers each XdndPosition at once with the operation the page gave for the previous one (none right after the pointer enters a window) and sends nothing more until the next position. GNOME's XWayland bridge sends positions only while the pointer moves and, on release, drops only when the last XdndStatus accepted, so a drag that stops right after reaching SlopAMP, or reaches it while the page is busy, was cancelled ("the first drag from a site does nothing"). The main process sends its own XdndStatus (accept, copy) to the drag source (the XdndSelection owner) each time the page accepts a `dragover`; that comes after Electron's answer to the same position, so the last word is the page's. Windows' OLE asks again by itself, so this is Linux only. `tests/linux-dnd-320.js` (`release_ms` in `xdnd-source.py`) fails without it.

**Links without "https://" in a Linux drop** (`dropUrls` in `app.js`): Chrome's address bar shows a page's address elided (no `https://`, no `www.`) until it's clicked, and a drag from it puts that text in `text/plain`; the full address is only in `text/x-moz-url`, which Electron on X11 decodes as UTF-16 and so never gives the page (patch (1) above only stops the crash). So on Linux, when the dragged data has no `http(s)://` link, a YouTube or X address without a scheme in `text/plain` (`BARE_WEB_RE`) is taken with `https://` in front; anything else still adds nothing. Found with a debug run on the captain's desktop (an X proxy logging SlopAMP's drag-and-drop traffic): the first drag from each site carried `youtube.com/watch?v=…`, the second `https://www.youtube.com/watch?v=…`. Windows gets the full link from Chrome and doesn't use this. `tests/linux-dnd-320.js` fails without it.

**Minimize to the tray on Linux X11** (`toTray()` in `main.js`): when the player is minimized, GNOME (Mutter) hides the windows transient for it (every other SlopAMP window) along with it: `WM_STATE` Iconic, `_NET_WM_STATE_HIDDEN`, still mapped; Electron then calls them minimized and not visible. `toTray()` hid only visible windows, so they stayed like that, and Mutter brings them back only when the player is un-minimized, not when it's withdrawn and mapped again (the tray's Show): only the player came back. On Linux it also hides a window that is minimized or that the layout has open (`wm.visible`). Windows calls a minimized window visible, so this is Linux only. `tests/linux-tray-320.js` (GNOME's minimize in `tests/fake-wm.py`) fails without it.

**The video window on Linux X11** (`windows.js`): Electron gives every window created with a `parent` the type `_NET_WM_WINDOW_TYPE_DIALOG`, and GNOME (Mutter) never lets a dialog go fullscreen, so the video window is created without one and gets the player with `setParentWindow()` right after (`WM_TRANSIENT_FOR`, so it still goes with the player). A normal window isn't kept out of the dock, Alt+Tab and the Overview the way dialogs are, and Electron's `skipTaskbar` does nothing on Linux, so `x11.js` sends the window manager the EWMH `_NET_WM_STATE_SKIP_TASKBAR` / `_SKIP_PAGER` request itself each time the window is shown (over its own short X11 connection; local displays only). `tests/linux-fullscreen-320.js` checks it under xvfb with `tests/fake-wm.py`, a tiny window manager with Mutter's fullscreen rule.

**Video encoders on Linux** (`media.js`): `h264_nvenc`, then `h264_vaapi`, then `h264_vulkan`, then `libopenh264`, each tried with a short test encode at startup. The BtbN FFmpeg build loads libva, libva-drm and libdrm itself on first use and *aborts* (a crash report on Ubuntu) when one is missing or too old; it needs libva 2.21+ (`vaMapBuffer2`), and Ubuntu 24.04 has 2.20. So `vaapiUsable()` looks for the three libraries first (FFmpeg's own `lib/`, `LD_LIBRARY_PATH`, the system folders) and checks that libva has `vaMapBuffer2`; otherwise VA-API is skipped and the log says why. Vulkan Video is loaded safely by FFmpeg and works on Ubuntu 24.04 with Mesa 25 (RADV, ANV). Both GPU encoders take frames in video memory: `hwUploadArgs()` adds the GPU (`-vaapi_device` / `-init_hw_device vulkan`) and `format=nv12,hwupload` at the end of the picture's filters to every finished ffmpeg command (the stream, the encoder test, CLIP's `run` / `runJob`); every other encoder's command is left exactly as it was.

`package.json`'s `desktopName` (`com.slopamp.SlopAMP.desktop`) is the menu entry's name; Electron uses it for the X11 window class and the media controls (MPRIS), so the dock and GNOME's media controls show SlopAMP's icon.

## Visualizer files

`src/renderer/vendor/butterchurn.min.js` and `src/renderer/vendor/butterchurn-presets.js` are committed, so a fresh clone runs without extra steps. ## Testing the updater

`bash build/make-update-test.sh` (after `build-win.sh`) makes `dist/update-test/`: three local release files (good, wrong SHA256, no SHA256 line) and a `.bat` for each, plus one for the portable exe. The installed-build `.bat` files find SlopAMP through the registry (uninstall `InstallLocation`, then `HKCU\Software\SlopAMP\InstallDir`, then the default folder). Each `.bat` starts SlopAMP with two environment variables:

- `SLOPAMP_UPDATE_TEST=<path to a release.json>`: read that file (same format as GitHub's release JSON) instead of GitHub, and check at every launch. The installer must be a plain file name next to it.
- `SLOPAMP_TEST_VERSION=1.1.9`: the version SlopAMP pretends to be, so the release counts as newer. Ignored without `SLOPAMP_UPDATE_TEST`.
- `SLOPAMP_TEST_PLATFORM=win32` (or `linux`, 3.2.0): the platform whose files SlopAMP looks for, so the Windows logic can be tried on Linux. Ignored without `SLOPAMP_UPDATE_TEST`.

The feed can also be a list of releases (GitHub's `/releases` format, newest first): the first full release counts as the latest, and the rest are where SlopAMP looks when that one has nothing for its platform. On Linux, start an AppImage with these variables to try its self-update; `tests/linux-320.js` checks the swap itself.

The About box shows TEST FEED while these are set. They are not passed on to the installer, so the reopened SlopAMP is a normal run and shows "Updated to X".

## Releasing

1. Bump `version` in `package.json` and add a section to `CHANGELOG.md`.
2. Build with `TOOLS=... bash build/build-win.sh` (Windows files) and `bash build/build-linux.sh` (Linux files; it prints their SHA256 lines).
3. Get the checksums: `cd dist && sha256sum SlopAMP-Setup-X.Y.Z.exe SlopAMP-Portable-X.Y.Z.exe SlopAMP-X.Y.Z-x86_64.AppImage SlopAMP-X.Y.Z-amd64.deb`.
4. Create a GitHub release tagged `vX.Y.Z` (not a pre-release) and attach the files. Write the notes in Markdown (the in-app "What's new" box shows headings, bullets, **bold**, `code` and links) and end them with one line per file, exactly in this form:

   ```
   SHA256 (SlopAMP-Setup-X.Y.Z.exe): <64 hex characters>
   SHA256 (SlopAMP-Portable-X.Y.Z.exe): <64 hex characters>
   SHA256 (SlopAMP-X.Y.Z-x86_64.AppImage): <64 hex characters>
   SHA256 (SlopAMP-X.Y.Z-amd64.deb): <64 hex characters>
   ```

   The auto-updater refuses a release whose notes have no `SHA256 (SlopAMP-Setup-X.Y.Z.exe)` line (Windows) or `SHA256 (SlopAMP-X.Y.Z-x86_64.AppImage)` line (the AppImage), or whose hash doesn't match the downloaded file. These lines are hidden from the "What's new" box.

   A release for only one platform (a Linux-only fix, say) leaves the other platform's files out; 3.2.0 and later on the other platform skip it quietly. Publish it **without "Set as the latest release"**: Windows copies older than 3.2.0 only look at the latest release and would show "Update stopped: no installer in the release" for it, while 3.2.0 and later find it in the list either way.
